# Исполнители, взаимодействие и передача результата

Это подготовленная архитектура. Активен только явно заказанный отдельный Sol для дашборда Насти. Массовый новый расчётный запуск ещё не начат.

## Роли

| Роль | Формат | Ответственность | Принимаемый результат |
|---|---|---|---|
| Координатор | Текущий Astra xhigh | Требования, выбор приоритетов, обновления коллег, назначение задач, паспорт и дашборд | Покрытие всех требований; условная рекомендация; точные изменения для команды |
| Методика | Существующий постоянный Astra xhigh | Общий сценарный контракт, календарь ресурса, единицы, экономика, условия выбора | Совместимый расчёт; реальные примеры; численные границы; сохранение авторских моделей |
| Данные и исходный бизнес | Sol 6.1 xhigh, конечная задача | Флот/поставки, действующая сеть и конкуренты, поддержка, источники, масштаб №2 | Датированные таблицы, наблюдение/оценка, покрытие затронутых пар; точные оставшиеся поля |
| Гипотезы и расчёт сети | Sol 6.1 xhigh, конечная задача | Все 35 карточек; новые комбинации; реализация утверждённого расчётного контракта | Обоснованные исходы; хаб/прямые/смешанный/KEEP; ресурс и экономика финалистов |
| Цифровые и коммерческие действия | Sol 6.1 xhigh, конечная задача | Конкретные пользовательские пути, дополнения продукта/партнёрств, границы эффекта | Законченные доказательные карточки, макеты/скрины, пороги; PNG для приложения |
| Независимая проверка | Свежий Sol 6.1 xhigh на конкретный пакет | Соответствие кейсу, входы, арифметика, контрпример, пользовательская понятность | Замечания с влиянием на решение, а не только успешный запуск тестов |

Одновременно максимум четыре Sol суммарно, включая пользовательский отдельный тред. Это роли, не требование запустить все сразу. Пока тред Насти работает, он занимает один слот; он проверяет новую исходную модель и UI. Затем слот используется для независимой проверки следующих точных пакетов. Три производственных задачи и один слот проверки — верхняя схема; приоритеты корректирует root. Sol не создают детей и не назначают задачи друг другу. Только root запускает новых исполнителей.

Два постоянных Astra нужны из-за накопленной методики и необходимости удерживать конечную задачу. Остальные задания конечные и проверяемые; постоянные треды для каждого CSV не нужны. Пользовательский тред Насти — явное исключение по форме, не дополнительный бесконтрольный пул.

## Обмен и обратная связь

Поток: root фиксирует вопрос и входы → исполнитель получает ограниченный пакет → отдаёт результат с SHA, периодом, единицами, примером и изменившимся выводом → независимая проверка → владелец исправляет существенные ошибки → root принимает точный вариант и отражает влияние в паспорте.

Astra методики передаёт root конкретные запросы на данные/проверку и готовые спецификации. Root передаёт их нужному исполнителю. Прямых рассылок всем агентам нет. Сообщения — готовый пакет, существенное препятствие, новое условие или изменение вывода. Рабочие детали живут в Git. Новый review/recheck — новая отдельная задача на exact SHA; исправления небольших замечаний делает владелец/координатор без дополнительного дерева агентов.

В brief каждого исполнителя: вопрос пользователя; версия входов; таблица/формула и смысл результата; границы записи; критерий готовности; срок; что нельзя объявлять доказанным; куда передавать результат. Недостающий показатель сопровождается поиском источника и анализом порога, а не только UNKNOWN. Успешная проверка счёта не принимает рынок или ресурс.

## Проверка коллег и GitHub

Root запускает `python3 scripts/check_colleague_updates.py --fetch` каждые 30–45 минут активной работы, перед новым существенным расчётом и сборкой. Проверяются опубликованные refs, авторство, точные file diffs и влияние на вывод. Это не polling агентов и не новый бесконечный монитор. Исполнителям передаются лишь нужные изменения и exact SHA. Merge/rebase чужих веток не выполняются.

Каждое изменение классифицируется: новые данные, исправление ошибки, новая модельная политика, изменение интерфейса или только текст. Численное влияние проверяется на реальном примере. Последний коммит не получает автоматически статус лучшей модели; старый отрицательный вердикт не приклеивается к исправленному коду.

Содержательные наши пакеты коммитятся и пушатся в собственные ветки: постановка; источник/расчёт; проверка; итоговый срез. В README — входной SHA, что изменилось, какие утверждения готовы, что требуется Насте. Не надо ждать 22:00 для единственной большой выгрузки. Внешние сообщения коллегам не отправляем без отдельного указания.

## Передача Насте

Основной дашборд сохраняет её композицию: города/веса → конкуренты → спрос → хаб/прямые → выбор/рост → карта/маршруты → дорожная карта/риски → источники. Новая версия 4a976356 уже содержит эти блоки. Не проектируем их заново.

Поставляем совместимые CSV/JSON и адресные предложения: добавить календарь/частичные поставки к `fleet_ramp`; было/стало и конкурентов к выбранной сети; отделить поддержку и полный результат от вклада; источник/метод/период и условия в раскрывающейся детализации. Авторские данные остаются исходной версией рядом с проверенным кандидатом. Финальное внедрение — владельцу дашборда, без самовольной публикации.

Дополнительные вопросы: отдельные изображения PNG и, при необходимости, PDF. Для цифровизации — проверенный нынешний путь, предлагаемый путь и порог эффекта. Для общей стратегии — масштаб цели №2, вклад первого этапа и условия следующего. К каждому изображению краткий вывод и источник. В паспорт только существенные тезисы; подробная причинная цепочка в приложении.
