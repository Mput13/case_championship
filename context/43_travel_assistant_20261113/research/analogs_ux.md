# Red Wings Travel Assistant: аналоги и демонстрационный MVP

Проверено 13.11.2026 по официальным сайтам, справке и документации через web search/fetch. Реестр URL, подтверждений и ограничений — [analogs_sources.json](analogs_sources.json). Это исследование продукта; покупка билетов, вызовы транспортных API с ключами, работа интерфейсов и доступность хостинга из сети участников не проверялись. Номера источников соответствуют реестру.

## Продуктовое решение

Узкий MVP: помощник по поездкам внутри России, который показывает **до трёх проверяемых цепочек с участком Red Wings** и ссылками на каждый участок. Начальный ввод — города и период; адрес необязателен. Второй режим закрепляет уже выбранный/купленный рейс RW и подбирает подъезд к нему, продолжение после него либо оба участка. Для быстрого прототипа лучше небольшой явно обозначенный набор направлений с данными, чем обещание полного покрытия России.

Польза для пассажира — сравнить всю поездку, включая ожидание и переезд между аэропортом и вокзалом. Продуктовая гипотеза для RW — показать достижимые города за пределами собственной маршрутной сети и снизить трудность планирования. Влияние на продажи или долю рынка этим исследованием не установлено.

## Два сценария пользователя

| Вопрос | A → B с обязательным RW | Рейс RW уже выбран / куплен |
|---|---|---|
| Что известно | Города, интервал выезда; при необходимости срок прибытия | Номер, дата, аэропорты, время конкретного перелёта; начало/конец всей поездки |
| Что ищем | Подходящие RW-участки и наземные сегменты вокруг них | Только свободные участки вокруг закреплённого перелёта |
| Как проверяем время | Прямой поиск по периоду с проверкой всех переходов | Подъезд — обратным расчётом от вылета; продолжение — от прилёта с получением багажа и переходом |
| Главное ограничение | В итоговой цепочке есть подтверждённый участок RW | Ассистент не меняет выбранный рейс при оптимизации |
| Цена | Полная сопоставимая сумма либо известная часть с перечислением пропусков | Отдельно стоимость подъезда/продолжения. Уже оплаченный перелёт не выдаётся за новый расход; его неизвестная цена не равна нулю |
| Если нет результата | Нет подходящей RW-цепочки в проверенных данных; предложить изменить даты/географию | Сохранить перелёт, показать, какой участок не удалось подобрать; предложить другой наземный выезд или продолжение на следующий день |

## Ввод и карточки

**Два обязательных шага ввода, третий — только при неоднозначности.**

1. Выбрать «Подобрать поездку» или «У меня есть рейс RW». В первом режиме: откуда, куда, дата/интервал **выезда**. Во втором: номер и дата рейса или ручные аэропорты/местное время из билета; город начала/конца и «до рейса / после рейса / оба». Не нужны фамилия, PNR и паспорт.
2. Показать распознанные условия с возможностью поправить. По умолчанию один взрослый, адрес не требуется; необязательны срок прибытия, багаж, бюджет и приоритет. Если адреса нет, явно назвать используемый городской узел и считать время до него: не выдавать путь «от двери» за известный.
3. Спросить только о критической неоднозначности: например, какой город с одинаковым названием или какой аэропорт указан в билете. В остальных случаях сразу показать варианты.

Карточка: последовательность городских узлов/вокзалов/аэропортов и видов транспорта; выделенный участок RW; местные даты/время и общая длительность; ожидания и переезды; число смен транспорта; цена с составом; ссылки по сегментам. Один короткий текст объясняет различие: например, «Меньше переездов между вокзалами». В подробностях — источник каждого участка и время проверки.

Показывать **две–три различные допустимые цепочки, если они есть**. Если цепочка одна, показывать одну. Не создавать три копии ради количества. Один вариант может получить несколько отметок:

- **Быстрее** — минимальное время всей поездки среди полностью рассчитанных цепочек с одинаковыми границами. Полётное время само по себе не критерий.
- **Проще** — сначала меньше пересадок/смен транспортного средства, затем меньше смен вокзала или аэропорта, затем меньше ожидания; ночёвку показывать явно. Это правило MVP, не измеренная вероятность успеха пересадки.
- **Меньше по известной полной цене** — только среди цепочек с сопоставимой полной ценой на дату, число пассажиров и условия багажа. Неполные цены не участвуют в этом ранжировании. Если полных цен нет, отметку убрать; написать «Известна цена 2 из 4 участков», а не «Самый дешёвый».

## Как получать цепочки и ссылки

Предлагаемый минимальный процесс:

1. Нормализовать города в проверенные идентификаторы; аэропорты, вокзалы и городские точки хранить раздельно. Москва не заменяет VKO/SVO/DME/ZIA. Период развернуть в календарные даты с часовыми поясами.
2. Получить датированные сегменты из доступного транспортного источника. Для быстрого демо допустим небольшой датированный набор, собранный вручную из источников, с видимой отметкой «Демонстрационный набор, проверен …». Не переключать его на видимость live при отказе API.
3. В первом режиме начать с подтверждённых RW-перелётов, затем достроить подъезд и продолжение; во втором использовать закреплённый рейс. Принадлежность RW проверять по перевозчику в источнике, не по свободному тексту модели. Не ограничиваться фильтрацией готовых результатов A → B: такой поиск может вообще не вернуть подходящий RW-участок. Для MVP ограничить набор узлов и число пересадок, раскрыть эти границы покрытия.
4. Сопоставить станции и реальные переезды. Проверять `следующее отправление ≥ предыдущее прибытие + высадка/багаж + переход/переезд + принятый запас`. Перед авиарейсом учитывать установленное перевозчиком закрытие регистрации/посадки и время аэропортовых процедур. Числа запаса — настраиваемое предположение продукта с источником/основанием, не универсальная гарантия. Неизвестный переезд не превращать в ноль.
5. Рассчитать длительности/цены и отобрать разные варианты обычным кодом. DeepSeek получает только их идентификаторы и данные для объяснения.

Для Яндекс Расписаний документирован `search` с `date`, `transfers=true` и типами транспорта; нужны ключ и обработка страниц ответа. При этом контракт подробной структуры пересадочного ответа следует проверить реальным запросом: публичное описание не заменяет проверку интеграции. Нынешняя документация рекомендует домен `api.rasp.yandex-net.ru`. [API](https://yandex.ru/dev/rasp/doc/ru/reference/schedule-point-point), [Доступ](https://yandex.ru/dev/rasp/doc/ru/concepts/access) (Y02, Y04).

**Ссылки формирует адаптер, не LLM.** У сегмента хранить тип ссылки: `offer` (конкретное предложение), `route_search` (направление/поиск), `operator_home` (главная перевозчика), `ground_route` (переезд). Сохранять реальный URL из ответа поставщика либо проверенную страницу направления. `thread_method_link` с API-ключом не отдавать посетителю. На главную RW допустима кнопка «Проверить билет на Red Wings», но нельзя подписывать её как покупку конкретного тарифа с сохранённой ценой. При отсутствии проверенного deep link показать параметры для повторного поиска и кнопку копирования; не изобретать URL-параметры.

Примеры проверенных страниц направления: [Нижний Новгород → Владимир, поезд](https://www.tutu.ru/poezda/Nizhnij-Novgorod/Vladimir/), [Екатеринбург → Нижний Тагил, поезд](https://www.tutu.ru/poezda/Ekaterinburg-Pass/Nizhniy-Tagil/), [Екатеринбург → Нижний Тагил, автобус](https://bus.tutu.ru/raspisanie/gorod_Ekaterinburg/gorod_Nizhnij-Tagil/). Они **не подтверждают** места, стыковку и цену на выбранную пользователем дату (G01–G03).

При использовании API Яндекса учитывать заявленную область бесплатного открытого сервиса и требования указания источника/ссылок. Пункт 3.2.4 ограничивает сохранение и обработку данных за пределами временного кэширования в рамках возможностей сервиса: не считать бесплатный API разрешением на постоянный собственный архив/датасет. Подготовленный набор для демо должен иметь подходящие условия использования источников. Точный лимит запросов не установлен этим исследованием: не закладывать неподтверждённые «500 в сутки». [Условия](https://yandex.ru/legal/rasp_api/ru) (Y05).

## Чем это отличается от LLM без transport tools

| Задача | DeepSeek без транспортных инструментов | MVP с проверяемыми данными |
|---|---|---|
| Понять «из Самары в Тагил, рейс уже куплен» | Может извлечь намерение и задать уточнение | То же, затем использует закреплённый сегмент |
| Подтвердить RW на конкретную дату | Текст модели не подтверждает расписание, выполнение или продажу | Датированный источник + перевозчик + аэропорты + статус |
| Собрать пересадку | Может предложить правдоподобную идею | Проверка дат, зон, станций, переходов и принятых запасов кодом |
| Сравнить расходы | Может объяснить известные значения; нельзя поручать восполнение пропусков | Расчёт только по полученным суммам, с покрытием цены |
| Открыть покупку | Сгенерированная ссылка может не существовать или не сохранять условия | URL поставщика/проверенный переход с точным типом ссылки |

Официальная документация DeepSeek прямо отделяет запрос tool call от исполнения функции приложением. Поэтому минимальные инструменты — `resolve_place`, `search_rw_segments`, `search_ground_segments`, `build_valid_options`; последний лучше считать на сервере детерминированно. LLM разбирает свободный текст и отвечает «почему этот вариант». Она не создаёт новые сегменты, цены и URL. [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/) (D01).

## Пустая выдача, неполные данные и отдельные билеты

| Состояние | Текст в интерфейсе | Следующее действие |
|---|---|---|
| Успешный поиск в объявленном покрытии не дал RW-цепочки | «В проверенных данных на эти даты не найден вариант с Red Wings» | Изменить даты; показать границы покрытия. Варианты без RW — только отдельным явно названным поиском |
| Источник недоступен / ключ отсутствует / покрытие неполное | «Не удалось проверить рейсы Red Wings на эти даты» | Повторить проверку или открыть официальный поиск; не заменять ошибку утверждением «RW не летает» |
| RW найден, наземный участок не подтверждён | «Рейс найден; продолжение до … пока не подтверждено» | Ссылки на проверку; отдельная неполная цепочка без отметок «быстрее/проще» |
| Цена части участков неизвестна | «Общая цена неизвестна. Известно … за …; не учтены …» | Проверить отсутствующие цены; не ранжировать как полностью оценённый вариант |
| Переход не укладывается в принятый запас | Не включать в готовые варианты | Найти следующее отправление/другую дату; при отсутствии — объяснить причину |
| Сервис использует сохранённые данные | «Демонстрационные данные от …» | Открыть исходный источник; не обещать актуальность продажи |

В раскрытии каждой составной поездки: **«Отдельные билеты. При задержке одного участка следующий билет может потребовать обмена или новой покупки. Запас времени не гарантирует стыковку».** Не писать «единый билет», «защищённая пересадка», «мы пересадим бесплатно» без отдельного подтверждённого продукта/договора. Туту также предупреждает об ограничениях при самостоятельно составленных пересадках. [Справка Туту](https://avia.tutu.ru/2read/avia/88_faq/) (T02). Это граница обещания MVP, не универсальное заключение о правах по любому договору.

## Три сценария для демонстрации

Официальное [табло RW](https://flyredwings.com/flight-board/) при чтении 13.11.2026 содержало в группе текущего дня **WZ 5029 Екатеринбург/Кольцово → Нижний Новгород/Стригино** и **WZ 1034 Самара/Курумоч → Екатеринбург/Кольцово** (RW01). Они служат опорой для выбора географии. Табло показывает фактические/плановые движения и местное время, а не тарифы или наличие билетов. Ниже нет утверждения о повторении этих рейсов на будущую дату. У завершённого рейса допустим только явно названный исторический демонстрационный сценарий.

### 1. Вся поездка: Екатеринбург → Владимир

Ввод: «Из Екатеринбурга во Владимир; выехать 20–22 ноября; один взрослый». Это **запрос для проверки**, не найденный перелёт. Проверяемая конструкция: городской узел → SVX → RW → GOJ → конкретный нижегородский вокзал → поезд → Владимир. Существование страницы наземного направления подтверждено (G01).

Варианты-кандидаты: RW + общественный транспорт до вокзала + поезд; тот же авиасегмент + такси до вокзала + другой допустимый поезд; RW + прямой автомобильный трансфер до Владимира, только если получен расчёт такого трансфера. Каждый обязан включать также подъезд к SVX. Для двух–трёх готовых карточек заранее получить датированные наземные сегменты и длительности переездов. Третий кандидат без данных не показывать как готовый маршрут. Ранжирование может выбрать одну и ту же цепочку по времени и цене.

Демонстрирует город назначения вне непосредственного RW-перелёта, ожидания и несколько видов транспорта. Ссылки: официальный поиск RW, страница поезда, проверенный маршрут каждого переезда. Если RW на выбранные даты не подтверждён, результатом этого же сценария будет честное соответствующее состояние.

### 2. Рейс закреплён: Самара → Екатеринбург, затем Нижний Тагил

Ввод: «Рейс RW уже выбран; дата из моего билета; после прилёта хочу в Нижний Тагил». Пользователь вводит/подтверждает реальную дату и время. Географическая опора — WZ 1034, замеченный 13 ноября; не подставлять этот номер на другую дату автоматически.

Кандидаты продолжения: Кольцово → Екатеринбург-Пасс. → поезд; Кольцово → конкретный автовокзал → автобус; автомобильный трансфер из Кольцово, если есть источник времени/цены. Страницы ж/д и автобусного направления существуют (G02–G03); конкретный наземный рейс после прилёта ещё требуется подобрать. При отсутствии актуального билета можно показать подписанный исторический пример с данными 13 ноября и сохранёнными источниками, не выдавая его за live.

Демонстрирует неизменность авиасегмента и отдельную стоимость продолжения. Переключатель «Нужен и подъезд» добавляет наземный путь до Курумоча обратным расчётом. Ошибка даты или слишком позднее прибытие не должна приводить к незаметной замене RW-рейса.

### 3. Не найден RW / недоступен источник

Ввод: «Архангельск → Вологда, 20–22 ноября». **Здесь не утверждается отсутствие рейсов RW.** Для воспроизводимого показа использовать подписанный демонстрационный ответ с пустым набором RW в ограниченном покрытии; затем тем же запросом смоделировать таймаут источника. Это два разных состояния одного сценария.

В первом случае показать отсутствие результата именно в проверенном наборе; во втором — невозможность проверки. Предложить новые даты/официальный поиск, а для полного повторного поиска без обязательного RW — отдельное действие пользователя. Дополнительный переключаемый пример: найден RW, но не получена цена или путь аэропорт → вокзал; не добавлять недостающий сегмент текстом модели. Демонстрирует честное поведение на произвольном вводе участников.

## Быстрый прототип на DeepSeek и доступ участников

Предлагаемый объём: одна веб-страница, два режима ввода, до трёх карточек, раскрытие сегментов/ссылок, три предустановленных сценария. Один серверный обработчик вызывает DeepSeek; транспортный адаптер работает с подготовленным набором либо доступным API. Имена инструментов выше — наш контракт, не существующий API Red Wings. Не включать оплату, PNR, аккаунты пассажиров, уведомления о задержках и гостиницы в первый показ.

Минимальные поля сегмента: `id`, `mode`, `from_station`, `to_station`, `departure_at`, `arrival_at`, `operator`, `flight_number`, `price`, `price_status`, `source_url`, `checked_at`, `link_type`, `booking_url`. Время — с UTC offset; неизвестные — `null`. У цепочки отдельно: переходы с основанием длительности, проверка запасов, полнота расписания/цен, закреплённый сегмент, использованные источники. Ввод из билета помечать как пользовательский, пока он не сверён с источником.

Для публикации подходит обычный HTTPS-хостинг с серверной функцией. Конкретный быстрый вариант — Vercel: документация подтверждает URL развёртывания и серверные переменные окружения. [Среды](https://vercel.com/docs/deployments/environments), [Переменные](https://vercel.com/docs/environment-variables) (H01–H02). Ключ DeepSeek хранить только на сервере, модель задавать конфигурацией; транспортные ключи не отдавать в браузер. Для презентации нужны общий URL/QR, отсутствие обязательного Vercel-login у посетителя и проба с телефона через мобильную сеть в России. Доступность такого размещения участникам, лимиты, стоимость и фактический deployment здесь **NOT_RUN**; рекомендация не является обещанием доступности из любой сети.

Порядок реализации: форма и расчёт по подготовленным сегментам → объяснение DeepSeek → реальные адаптеры при наличии доступа → размещение и проба участником. Если данные подготовлены вручную, показать это в интерфейсе. Если LLM недоступна, сохранить карточки и ссылки; если транспортных данных нет, не имитировать их генерацией.

Для приёмки демо достаточно проверить: каждый готовый вариант содержит RW и непрерывную датированную цепочку; закреплённый рейс не меняется; аэропорт и вокзал не склеены в одну точку; учтены переходы и часовые пояса; неполная цена не выигрывает сравнение; ссылки соответствуют типу и направлению; пустой набор отличается от отказа источника; сохранённые данные подписаны; участник открывает URL с телефона и не получает ключи API.
