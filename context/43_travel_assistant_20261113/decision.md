# Red Wings Travel Assistant: решение для прототипа

13.11.2026. Исследования: [аналоги](research/analogs_ux.md), [коннекторы](research/connectors.md), [Pi и размещение](research/runtime_hosting.md), [Trip&Fly](research/tripfly.md), [контекст презентации](research/presentation_context.md).

## Продукт

Два входа: маршрут по городам/периоду; уже выбранный рейс Red Wings. Начальный адрес необязателен. Целевой результат — до трёх различных транспортных цепочек с обязательным подтверждённым участком Red Wings. Если допустимых вариантов меньше, не создавать искусственные карточки. Отдельный будущий режим может использовать предлагаемую сеть 2027–2028, но не выдавать её за текущее расписание.

Расписания и код формируют цепочки, модель уточняет запрос и вызывает только предметные инструменты. Полнота времени/цен и право продажи показываются раздельно. В прототипе нет оплаты, оформления билета или действующей защиты стыковки.

## Технический выбор

Выбран Pi `@earendil-works/pi-agent-core` + `pi-ai` 1.5.2, Node.js. Модель — точный ID `deepseek-v4.1-flash`, авторизованный `GET /v1/models` вернул его 13.11.2026. МАИ работает через `/v1/chat/completions`. Ключ находится в защищённом файле T3; в репозиторий не копируется.

13.11.2026 12:50 UTC проверен настоящий цикл Pi → DeepSeek → `get_verified_flight` → результат инструмента → DeepSeek. Два HTTP POST, два модельных вызова, один инструмент, без повторов; нормальное окончание. Инструмент читал сохранённый реальный рейс, не live-инвентарь. Usage: 850 tokens по Pi за оба вызова; денежный тариф неизвестен. Receipt: [mai_pi_tool_smoke.json](receipts/mai_pi_tool_smoke.json). Это проверка транспорта и tool loop, не качества планировщика и не подключённый пассажирский E2E.

Проверка TLS сохранена: отдельный HTTPS-клиент доверяет официальному Russian Trusted Root CA только для хоста МАИ, с проверкой имени. Глобальное доверие, системные профили и процессы не меняются. Транспорт позволяет только один фиксированный endpoint, запрещает редиректы и ограничивает размер/время ответа.

## Источники

Яндекс Расписания — кандидат для датированных междугородних сегментов; ключ ещё не получен. Для адресного/городского участка — дополнительный 2ГИС Geocoder/Routing либо Яндекс Router; до доступа используем документированные внешние навигационные ссылки. Точное наличие мест, цены и покупка — отдельный билетный контур, кандидат «Инновационная мобильность» / White Label.

Условия использования источников должны определять допустимые функции. Обычный ключ Расписаний не даёт автоматически права на постоянный транспортный граф, перераспространение и любое объединение/ранжирование. Суточная квота нового ключа не подтверждена; число 500 не принимаем как текущий лимит. Для внешнего демо предпочтительны собственные/официально разрешённые данные или согласованный режим источника.

## Статус готовности

- Исследование и API-контракты: готовы, неизвестные перечислены.
- Интерфейс: интегрирован с HTTP API; HTML-render проверен на ширине 1280, 728 и 390 px, без ошибок консоли. Это не браузерный E2E.
- Первая реализация ядра: прямые RW-перелёты + наземные рекомендации; полноценный датированный мультимодальный поиск ещё не реализован.
- DeepSeek: текстовый ответ и настоящий Pi tool loop проверены.
- Transport live: ключ не получен, NOT_RUN.
- Размещение: пользователь выбрал оставить локальный прототип. Запущен `http://127.0.0.1:3080`, только loopback. Публикация исключена из текущего объёма.

Pi соединён с планом и интерфейсом: локальный HTTP smoke прошёл с настоящими вызовами модели, карточки формирует код. Свободные пожелания удалены из формы и отклоняются API, адреса влияют на ссылки. Два режима и границы проверены offline. Внешний показ, live-мультимодальные данные, геокодирование и реальные стыковки остаются следующим этапом; текущую основу нельзя объявлять готовым сервисом мультимодальных поездок.
