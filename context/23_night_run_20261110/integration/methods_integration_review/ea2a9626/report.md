На дне0 меняются начисления/запасы/обязательства без cash; день3 — избегаемый расчёт, день7 — один refund precollected net fare, день14 — условное снижение пополнения топлива. ## Сохранность и негативные входы

Все 12 common-v3 файлов неизменны относительно abb1 и c24; все шесть historical portfolio-v1 файлов неизменны относительно c24. Новый `portfolio_v1_replay` совпадает по значениям во всех шести файлах: только порядок calendar rows отличается. Отсортированные tail IDs не меняют суммы или календарные значения. Текущий replay пишет в отдельную папку (`portfolio_comparison.py:10`, `:38`). Новое common_demand.main после изменения simulate побайтово воспроизводит все свои семь файлов.

Проверены отказы при несовместимых shared D/fare/transfer/old cap, неверном source profile, исчезновении physical ID, дублировании capacity и замене HOLD NULL на0. Граница приёмки зафиксирована отдельно: дублирование N-itinerary в изменённом input не отвергается самой interaction.main и искажает две строки N/UFA4/base; независимый oracle отвергает duplicate key, а exact-byte manifest перестаёт совпадать. Это не дефект закреплённых входов и не основание требовать универсальный валидатор в MR11. Одобрение нельзя переносить на изменённый input_set без нового полного key/hash/oracle admission.
