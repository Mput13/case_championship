## Общая пара и отбор прямой сети

**Конкретное замечание B3 применено.** В latest `src/network_model.py:281–301` группирует плечи по `frozenset(a,b)`, складывает частоты F и один раз считает `min(demand × share(F), F × seats × lf_max)`. Затем поток делится между программами пропорционально частотам. Это общий пул одной физической пары внутри одной сравниваемой прямой сети, при допущении симметрии направлений. Он не доказывает общий наблюдённый OD-пул или устранение каннибализации относительно действующей сети RW.

Реальный пример base Москва—Омск: три программы с частотами 4+4+3 в неделю в каждую сторону; вход 674175 пассажиро-сегментов/год в обоих направлениях. Независимый захват тех же программ дал бы 87497,790; общий — **80581,036**, экспорт после построчного округления — **80581**. В `shared_pair_examples.csv` так проверены все шесть повторяющихся физических пар latest (три base, три cautious). Входы cautious отличаются: это `pax_cautious`, а не тот же наблюдённый поток. Для конкурентных пар частотная доля берётся из `f/(f+f_comp)` с cap; для остальных — насыщение capture. Проверены также seat cap и распределение в извлечённой точной функции `joint`.

`src/network_model.py:310–340`: прежняя сортировка отдельных треугольников заменена greedy по приросту результата всей сети / дополнительным блок-часам, с новым совместным пересчётом. Это существенное исправление отбора при общих плечах. Проверена работа точного `direct_network` на маленькой синтетической сети с повторяющимися плечами. **Глобальный оптимум не установлен:** shortlist ограничен 400 отдельно оценёнными треугольниками, частоты взяты из одиночной оценки, перестановка/удаление выбранных программ не выполняются. Минимум восемь программ заставляет включать отрицательный прирост; это авторская постановка, а не доказательство оптимальной стратегии компании.
