Насильно добавлять слабые рейсы не нужно: следует сравнить обе оптимизированные сети при общем верхнем ограничении ресурса и учесть стоимость/альтернативу свободных часов. Один резерв в GOJ и один резерв на две базы ZIA/SVX не дают одинаковую скорость восстановления. Публичный парк RW не равен свободным бортам проекта.

Б 0 при +10% уже имеет 6 исходных самолёто-дней выше 10 ч; при +20% — 9. Нельзя объявить Б 0 устойчивой по одному среднему налёту. ## 3. Как формируется OD и выбор

`inputs.json` содержит **31 уникальную пару**: 20 физических пар проектов плюс 11 дополнительных трансферных OD. Пересадочных OD у А 13: ARH–MRV и KUF–OMS уже входят в физические пары Б 0. Поэтому нельзя складывать 20+13 как 33 различных рынка.

Спрос `D` — число односторонних конечных авиапоездок всего рынка за неделю **в одном направлении** до выбора проекта. Одинаковое D подставлено в обратную сторону. Это сильное допущение, особенно для вахтовых/туристических потоков. Проектное предложение не создаёт этот D из числа кресел. 47 000/(2×52)=451,923 сегмента/нед./направление — лишь условная нормализация годового аналога, если исходное число включает оба направления и симметрию. Источник не показывает ни этих разрезов, ни зиму, ни конечные путешествия.

Для каждой доступной направленной OD алгоритм считает число пригодных датированных вариантов `f`, затем:

`q = qmax × (1 − exp(−f/3))`

`желаемые поездки = D × q`

В базе qmax равен 0,65 для `open`, 0,50 для `competitive`, 0,45 для `uncertain` ZIA и 0,45 для трансфера; осторожно — 0,50/0,35/0,30/0,30. Трансфер дополнительно умножается на сценарную поправку прямой конкуренции: 0,45 на AER–KUF/AER–UFA; 0,60 на MRV–OMS; 0,65 на MMK–MRV; 1 на прочих. Коэффициенты и скорость насыщения частотой не оценены. Цены/длина поездки/дни возврата/конкурентная частота не входят в полезность пассажира отдельными параметрами. `open` означает сценарную классификацию, а не доказанное отсутствие альтернатив; NJC–VOG, например, имеет неполный первичный календарь.

Бронирования равномерно делятся между пригодными днями. Нет сегментов «деловой/досуг/вахта», пики не оценены, переноса на другую дату при нехватке места нет. Местные брони размещаются первыми; внутри класса — по дополнительной марже на сегмент, затем лексикографически. Один билет берёт места на всех его рейсах. Это жадный детерминированный алгоритм, не максимум дохода всей сети. Дробные пассажиры — ожидаемый сценарный объём, не индивидуальные бронирования.

Для редактора: диапазоны OD надо подписывать «сценарная проверка, нижняя доказанная граница неизвестного рынка 0», не «прогноз спроса 80–220». Два сценария одновременно меняют спрос, выбор, доход, расходы и переток. Разница результатов между ними не является эффектом одного фактора и не имеет вероятности.

У созданной волны прилёт 12:00 UTC, вылет 13:15 UTC: ожидание **75 минут**. Это тестовая технология, а не подтверждённый MCT Red Wings в GOJ. Опубликованные в Уфе 1–4 часа нельзя автоматически переносить на GOJ, другую комбинацию перевозчиков или на защищённый сквозной продукт.

## 6. Затраты и арифметика результата

Для рейса продолжительностью h блок-часов:

`fuel_t = h × burn_t_per_h + fuel_t_per_cycle`

`flight_cost = fuel_t × (fuel_price + uplift) + h × (MRO + crew + navigation) + ground_basket × airport_factor + deicing_probability × operation_price`

Для всей сети:

`Δcontribution = gross_project_revenue − foregone_old_RW_revenue − new_flight_cost − new_passenger_cost + avoided_old_passenger_cost`

Расход топлива — **сценарные** 1,55 т/блок-час +0,20 т/цикл в базе; 1,90+0,25 осторожно. Это не расход, взятый из паспорта/фактического dispatch RW. Цены 133 200 и uplift1696 — первичные строки Уфы; их распространение на все рейсы — допущение. MRO/crew/nav 35/15/6 тыс. ₽ за блок-час в базе и 55/22/8 осторожно — сценарии. Обработка 25%×60 тыс. или 40%×100 тыс. — ожидаемый резерв без калиброванной погодной вероятности. Публичные 49 970/65 000 за процедуру SSJ не устанавливают полный расход материалов и договорный итог.

Корзина земли воспроизводится: `49,45×(553+499)+19 300+8100+16 668 = 96 089,40 ₽`. 49,45 т — паспортный ориентир LR, не измеренная МВМ всех RW; набор услуг и скидки отдельно проверяются. В `flight_costs.csv:3` OMS→GOJ h=3,25, топливо=5,2375 т, топливная сумма=706 517,80, MRO113750, crew48750, nav19500, земля 96089,40, резерв deice15000; итог **999 607,20 ₽**. Арифметика и единицы верны при этих входах.

В базе А получает 380,35 т топлива за неделю, Б 0 317,8125, Б 388,20417. Топливная статья А=51,308 млн ₽ из рейсовых 75,020 млн; Б 0=42,872 из 61,832. Неподтверждённый burn/маршрутный профиль поэтому существенно влияет и на абсолютный результат, и на разницу сетей.

Старые рейсы базово продолжаются. Ушедшие на проект пассажиры лишают RW прежней выручки; экономится только заданная пассажирозависимая статья. Топливо и рейсовый экипаж старого рейса не экономятся, пока сам рейс остаётся. Это правильная граница для **добавления** проекта. Не оценены освобождение старых мест для новых клиентов, возврат спроса, отмена/перенос старых рейсов, их remaining passengers. Часть старого трансферного потока задаётся без проверки календарной вместимости старой сети: потолок миграции найден лишь для трёх прямых пар, шести направлений.

`incumbent_redeployment_bound.csv` — только условный кредит в рамках тех же рейсовых ставок: А 1,922 млн, Б 0/Б 5,976 млн в базе. При простом прибавлении Б 0 становится лучше А, но это **не полный результат замены**: нет баланса потерянной старой выручки/пассажиров и новой схемы. Слово upper bound относится к кредиту при выбранных ставках, не к эмпирически доказанной максимальной экономии реальной RW.

Фиксированный парк/лизинг/капитал, запуск и выход, центральный аппарат, полноценная база/ТО/резерв, нерегулярность и денежные сроки здесь отсутствуют. Б 0 предполагает, что существующие базы примут проект без отдельного fixed платежа. Вход «net fare после сборов» нужно при дальнейшем сборе коммерческих данных согласовать с расходными строками аэропорта: одни и те же перечисляемые сборы нельзя вычесть дважды. Сейчас налоговая база условно без возмещаемого НДС; это не готовый бухгалтерский cash flow. `break_even_yield_cost.csv` называет yield то, что в колонках является доходом на поездку; в тексте применять ₽/поездку, не ₽/пасс-км.

## 8. Пороги: у каждого свой вопрос

**Цена базы относительно Б 0.** При базовых продажах допускается суммарно 2,78756 млн ₽/нед., или 144,95288 млн ₽ за 52 одинаковые недели, дополнительных фиксированных издержек А **относительно** Б 0. Лимит должен покрывать и базу, и разницу стоимости парка/капитала/резерва. При осторожных продажах он отрицательный. Это порог относительного сравнения, не бюджет прибыльного запуска.

**Сдвиг общих затрат.** `comparison_cost_thresholds.csv:2`: отдельно +74 833,70 ₽/блок-час, +116 148,14 ₽/рейс либо +44 574,14 ₽/т к общей цене топлива дают ничью А/Б 0 при прежних продажах и нулевой разнице fixed costs. Делители — 37,25 ч, 24 рейса, 62,5375 т соответственно. Не складывать эти три изменения как одновременный сценарий одной границы.

**Захват тех же трансферных рынков.** `capture_transfer_thresholds.csv:2,4,6`: при фиксированных OD/местных продажах и неизменной Б 0 А сравнивается с Б 0 при 1308,75/1367,24/1481,02 трансферных поездках за неделю для годового эквивалента базы 0/50/150 млн ₽. Базовая точка 1476,99. Это условные пороги определённого состава OD и цен; не универсальное число пересадок на любой хаб. При этих сценариях нулевая прибыль не достигается на проверенной сетке.

**Рост самого рынка.** `transfer_thresholds.csv:2,4,6` изменяет D всех 13 трансферных OD; Б 0/Б получают тот же рост на своих ARH–MRV и KUF–OMS. В базе окна преимущества А над лучшим прямым вариантом: при нулевой базе множитель 0,52987–2,06417; при 50 млн 0,60122–1,78848; при 150 млн 0,79128–0,95989. Поэтому рост рынка не обязан постоянно помогать А: общий прямой продукт тоже заполняется, а стыковки А ограничены плечами. Эти пороги нельзя смешивать с предыдущими 1309/1367/1481, где объём рынка фиксирован.

**NE-02: максимум не равен насыщению.** Осторожный `capture_transfer_thresholds.csv:8–13` сообщает `max_transfer_pax=1829,2102`, взятое из capture×1000. Но `capture_sensitivity.csv:312` при capture×5,3 даёт **1920,2865**, больше на 91,0763. Нелинейный жадный алгоритм меняет смесь OD. Исправить заголовок в «при максимальном capture» либо брать настоящий максимум сетки вместе с параметром. Наличие большей промежуточной точки не создаёт окупаемость: её вклад −93,359 млн против Б 0−87,503. Слово «max» особенно нельзя превращать в физическую ёмкость хаба.

**NE-03: отдельное прямое обслуживание.** `pair_thresholds.csv` делит рейсовые расходы пары на чистый вклад одного прямого пассажира без перетока/трансфера/fixed fleet/base. GOJ–KUF, А, строка 4:120,119 пассажира на вылет при 100 местах, т.е. местный прямой продукт по 4500 не покрывает эти расходы даже при полном борте. Для хабового луча это не достаточное основание закрытия: совместная сеть может получать трансферный вклад. AER–GSV, Б 0, строка 10:92,432 пассажира/вылет и 877,356 OD/нед./направление при заданной функции выбора, без перетока. OMS–SVX, Б 0, строка 20:98,488 и 934,835. Порог рынка не равен порогу проданных поездок и не является оценкой существующего D.

**Добавки Б.** `reinforcement_test.csv:2–5`: GSV–AER +8 рейсов даёт+162,544 поездки, +7,025 млн расходов и−5,554 млн вклада в базе. Точный условный порог D=1524,015/направление/нед.; base D600. ## 11. Что графики действительно показывают

`comparison_chart.html` строится из шести значений вклада и вычитает выбранную цену базы только из А: `A_value = contribution_A − annual_base/52`. Этот график доказывает только арифметику шести сценарных значений и чувствительность к **одному** фиксированному расходу. Он не пересчитывает продажи/частоты при движении слайдера, не показывает доверительный интервал, качество OD, доступность парка, NPV, риск, оптимальность GOJ или эффективность любой хабовой сети. | SVX–OMS может выдержать больше частот | Достаточный новый спрос и низкий реальный переток покрывают рейсы | При подтверждённом рынке/тарифах даже оптимальная частота даёт отрицательное приращение | Существующие 2 частоты RW, загрузка/цены/новые клиенты, контрактные расходы |
| UFA может превзойти GOJ как хаб | Лучшие договоры/OD/операционные условия компенсируют географию | Полная сопоставимая сеть UFA хуже по дополнительному вкладу и выполнимости | Независимый расчёт UFA, а не изменённые баллы |
| Один резерв достаточен | Доступный самолёт быстро покрывает отказ в нужном месте | Одновременный/удалённый отказ ведёт к неприемлемым отменам/кассовому ущербу | Позиции резерва, времена восстановления, история AOG/задержек |
| Замена старых частот выгоднее добавления | Снимаются реально избегаемые рейсовые расходы при сохранении ценного потока | Потеря старой выручки/сети и ограничение новых мест превышают экономию | Фактический baseline каждого снимаемого рейса, перераспределение всех OD |

Это исследовательские гипотезы; таблица не назначает ответственных и не фиксирует решения команды. В первую очередь нужны данные, способные перевернуть знак/порядок результатов: месячные OD и тарифы, baseline RW, расход/контракты, доступный парк и условия GOJ/UFA. Затем оптимизировать пары/частоты при общем ресурсе, проверить совместные adverse scenarios, только после этого считать инвестиционный горизонт/долю/пилот. Универсальный LF или score не заменяют правило запуска.

## 13. Замечания к коду и воспроизводимости

- Основные инварианты `evaluate():258–275` полезны: границы мест, OD+transfer=segments, миграция≤продажи, gross соответствует применённому тарифу, желаемые продажи≤сценарного D. Они не проверяют эмпиричность D или контракта.
- `validation.json` перечисляет входные хеши, но не включает **`context/11_practical_screening/ranking.csv`**, который читает `update_city_ranking():556` и от которого зависят рейтинги. Для этого commit файл зафиксирован Git, но сам manifest неполон для проверки отдельно скопированной папки. Минимально добавить hash ranking.csv; данные рынка не пересчитывать из рейтинга.
- `planning_cap_block_h` и `spare_scenario` есть во входах, но operational code использует жёсткое 10, а стоимость/позицию spare не считает. Для нынешнего входа 10 арифметика верна; редактирование поля может создать ложное ощущение изменения сценария. Подключить параметр или обозначить как декларативный; резерв моделировать отдельно.
- `collect_network_sources.py` воспроизводит извлечение только при наличии raw cache; сырые страницы в Git не сохранены, а доступность будущего URL не гарантирует старый текст. Экономика по frozen JSON воспроизводима; парсер по архивному HTML в этом аудите **NOT_RUN**. Проверено чтением кода, что сохраняются hashes и выбираются активные дни UFA. `accessed` берётся изmtime файла, а не из серверного времени запроса; копирование cache с изменениемmtime может изменить дату. Метаданные не полноценный архив исходных публикаций.
- Парсер считает покрытие аэропорта полным по наличию подходящего HTML, не проверяет отдельный контракт структуры/количество строк. Сейчас сохранены осмысленные строки; при будущем изменении верстки нулевой результат нельзя классифицировать как отсутствие рейсов. Нужны явная проверка извлечения и UNKNOWN при parse failure, прежде чем применять новую версию к решению.
- `datepart()` привязан к зиме 2026/27; переиспользование без смены года недопустимо. Пороговые binary searches — условные расчёты на сетке и заданной смеси, не доказательства глобальной оптимальности. Для примера NE-02 монотонность продаж уже нарушена жадной аллокацией.
- Фиксированные seed/topology и сценарные fares/choice не стали «моделью риска» от успешных conservation assertions. Отдельный `PASS` нужен будет каждому следующему слою: источники, статистика, производственный план, коммерческий результат.
