# Спрос, выбор пассажира и чистая выручка — P05

Пакет содержит исполняемую сценарную модель для самостоятельного `CASE_SJ`: 415 ненаправленных внутренних пар, 830 направлений, 24 месяца 2027–2028, два сценария, 39 840 строк. `base/cautious` — разные условия расчёта, **не доверительный интервал**. Международные и отсутствующие в авторской географии узлы вынесены в `market_exclusions.csv`; это не нулевой спрос. P02I подключается отдельной закреплённой версией.

Основные выходы: `od_monthly.csv`, `choice_model.json`, `net_yield.csv`, `validation.json`. Для общего ядра: `producer_fragments.json`, `ordered_legs.csv` и `engine_interface/`. Метод и границы подробнее описаны в `report.md`; определения всех выбранных значений — в `assumptions_register.json` (`P05-A01`…`P05-A16`).

## Расчёт

Из корня репозитория:

```sh
python3 context/35_full_programme_execution_20261112/P05/build.py
python3 context/35_full_programme_execution_20261112/P05/check_engine.py
python3 context/35_full_programme_execution_20261112/P05/validate.py
python3 context/35_full_programme_execution_20261112/P05/package_notes.py
python3 context/35_full_programme_execution_20261112/P05/seal.py
```

Для этих команд достаточно стандартной библиотеки Python 3.11+. Сетевые запросы не выполняются. Источники уже сохранены и хешированы. Необязательное повторное извлечение исходных XLS использует `xlrd==2.0.2` и `extract_monthly.py`; оно не требуется для воспроизведения модели.

`model.py --flights-json FILE --scenario base --output .../P05/fragment.json` принимает **заранее подготовленные датированные сценарные рейсы RW**. Он не преобразует station-pair оферы P02 в физические вылеты. Другие операторы и существующий бизнес добавляются координатором через собственные принятые таблицы и один общий пересчёт. Автоматическое наращивание или годовое копирование диагностической недели не выполняется.

## Что проверено

На закреплённом P06 `bc70308fe091c5767dbf26b02d06a7d750a65614` выполнены `evaluate`, `compare`, `scenario` с реальными ID пакетов P03/P05. Распределение поездок выполняется; общий парк и спрос сохранены в P/KEEP. Полный операционный результат и финансирование остаются `null`: расходы, денежные условия и весь будущий KEEP не установлены. Это проверка совместимости интерфейса и условной модели, не приёмка эксплуатационного ресурса или стратегии Red Wings.

P03 в этом pin содержит 60 рейсов только 11–17 декабря 2028. Продукты P05 используют их точные ID, время и общий остаток кресел. Спрос нарезан по датам, поэтому месячный объём не продаётся целиком в выбранную неделю. Произвольное умножение результата на 52 запрещено.

Проверка сезонного профиля на первичных месяцах 2026 отделена от проверки сегментного прокси. Независимых наблюдений конечного OD и booking choices нет; OD и поведенческие параметры остаются сценарными. Автор пакета не проводит его независимую приёмку.

## Интеграция

`producer_fragments.json[base|cautious][project|keep]` содержит принадлежащие P05 `markets/products/contracts/choice_model/response_policy/assumptions`. Поля рынка `lower/upper=null` означают неизвестные эмпирические границы; в CSV это `UNKNOWN`. Сторонние источники, их даты и SHA не подменяются живой веткой.

Остаточный существующий авиарынок представлен `outside_component=UNREPRESENTED_EXISTING_AIR`: это сценарная масса выбора без придуманного физического инвентаря. `NO_TRAVEL` хранится отдельно. Эти массы не являются измеренными перевозками или сегментами конкурентов. Собственные существующие продажи RW и их переток **не установлены**; диагностический KEEP без физических рейсов RW нельзя принимать как весь бизнес без проекта.

Чистая выручка уже уменьшена на сценарные комиссии/эквайринг. При интеграции P04 соответствующие расходы нельзя списывать второй раз. Аэропортовые и прочие производственные расходы остаются в P04. Доходы и затраты на контрактные блоки требуют отдельного явного контракта; пустой `contracts` здесь относится к условным новым розничным продуктам, не ко всем контрактам RW.

`engine_scope_counterexample.json` воспроизводит дефект раннего P06: триггер реакции конкурента суммирует частоту между месяцами/сегментами. `materialize_response` связывает триггер с конкретным месяцем и датированной когортой. Такие materialized P/KEEP policies могут различаться; ранний `compare` требует одинаковые объекты и потому проверен здесь только с общей passive policy. Динамическая реакция проверена через allocation, не объявлена принятой в общем сравнении.

Для финального расчёта требуются поля из `dependency_requests.csv`. Изменение затронутого источника или параметра требует повторить соответствующий расчёт, а не весь исторический корпус.
